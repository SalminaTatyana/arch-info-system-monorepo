ПРЕДЛОЖЕНИЯ ПО УЛУЧШЕНИЮ (сверх требований)
Дата: 01.11.2026 | Основание: ветка main, коммит b161057
Это не замечания: ниже только то, чего в требованиях нет и что можно добавить
добровольно. Порядок — по отдаче: сначала сквозные улучшения, потом по командам.

================================================================================
А. СКВОЗНЫЕ УЛУЧШЕНИЯ (поднимают систему целиком)
================================================================================

А1. ОДИН ДЕМОНСТРАЦИОННЫЙ СЦЕНАРИЙ НА ОБЩИХ ДАННЫХ
   Сейчас: у каждой команды свой набор данных, сквозной истории нет — на защите
   показываешь шесть отдельных стендов.
   Предложение: собрать общий набор: сотрудник → проект → эпик → задача →
   прогон → дефект → отчёт, и связать записи одним ключом (account_user_id).
   Каждая команда добавляет свои данные по тем же ключам.
   Зачем: демонстрация «от приёма сотрудника до отчёта» вместо шести отдельных
   экранов; сразу видно, что система собрана, а не набор модулей.
   Как: инфраструктура даёт каркас набора (кто, какой проект), команды
   дополняют; данные кладутся в seed и поднимаются вместе со средой.

А2. СКВОЗНАЯ ТРАССИРОВКА ОПЕРАЦИЙ
   Сейчас: телеметрия есть у инфраструктуры и справочников, у остальных её нет;
   по журналам нельзя проследить одну операцию через модули.
   Предложение: единый идентификатор запроса из общего входа, который все модули
   передают дальше и пишут в журнал; в коллекторе — поиск по нему.
   Зачем: разбор любой сквозной операции за минуту, сильный ответ на вопрос
   «как вы отлаживаете интеграции».

А3. СТРАНИЦА СОСТОЯНИЯ СИСТЕМЫ
   Сейчас: проверки готовности есть у каждой подсистемы, но смотреть их можно
   только по одной.
   Предложение: одна страница: вход, очередь, хранилище, базы, модули, версии
   образов, когда обновлялись данные.
   Зачем: на защите одна кнопка «система жива»; при сбое сразу видно, где.

А4. КОНТРАКТНЫЕ ПРОВЕРКИ МЕЖДУ ПАРАМИ
   Сейчас: одна команда (тестирование) проверяет реализацию против спецификации,
   остальные пары договариваются словами.
   Предложение: общий шаблон проверки «потребитель сверяет поставщика по
   спецификации» и его подключение у каждой пары обмена.
   Зачем: расхождение полей ловится до защиты, а не на демонстрации.

А5. ЕЖЕДНЕВНЫЙ ЖУРНАЛ ИНТЕГРАЦИЙ
   Сейчас: проверяются рабочие примеры инфраструктуры, а не реальные связи
   модулей.
   Предложение: раз в сутки автоматически дергать каждую пару обмена и
   публиковать отчёт «кто кого не видит».
   Зачем: к защите накапливается история, что связи действительно работали.

А6. ЕДИНЫЙ ШАБЛОН ЗАМЕРА ПРОИЗВОДИТЕЛЬНОСТИ
   Сейчас: замер есть только у отчётности (миллион строк, процентили, артефакт).
   Предложение: взять её подход как шаблон (сценарий, инструмент, артефакт,
   порог) и прогнать остальным модулям.
   Зачем: заявления о скорости подтверждаются числами, а не словами.

А7. СВОДНЫЙ ГЛОССАРИЙ И КАРТА ОБМЕНА
   Сейчас: у каждой команды свой глоссарий, сводного нет; каталог контрактов
   есть у инфраструктуры, но графа обмена «кто с кем и чем» нет.
   Предложение: один документ «термины системы» + схема обмена по видам
   интеграций.
   Зачем: снимает половину споров о терминах и попадает в критерий качества
   документации.

================================================================================
Б. ПО КОМАНДАМ
================================================================================

Б1. МОДУЛЬ УЧЁТА РАБОТ
  1. Массовые операции над задачами (смена статуса, исполнителя, итерации
     пачкой) — сейчас их нет, а в работе с бэклогом без них тяжело.
  2. Сохранённые фильтры и представления списка — своего не нашли ни у кого.
  3. Эскалация по срокам: подсветка просроченных и уведомление ответственному
     через общий сервис рассылок (когда он появится).
  4. Показать связи задач на доске (блокирует, связано, подзадача) — в данных
     связи есть, на экране их не видно.
  Зачем: это то, что делает трекер рабочим инструментом, а не демонстрацией.

Б2. МОДУЛЬ ПЛАНИРОВАНИЯ
  1. Экран сравнения версий плана: что изменилось между версиями (состав,
     сроки, бюджет, ресурсы) — версии и подтверждение ресурсов у вас есть.
  2. Предложение варианта распределения по ограничениям доступности (жадный
     алгоритм) с показом дельты бюджета — как подсказка, решение за человеком.
  3. Экран «план против факта» с процентом отклонения и прогнозом завершения —
     данные факта от учёта работ уже приходят.
  Зачем: закрывает главный вопрос руководителя — «успеваем или нет».

Б3. СПРАВОЧНИКИ
  1. Срез справочника на дату (параметр «на дату») — ревизии у вас есть, и это
     даст отчётности исторические срезы без ручной работы.
  2. Групповая правка окладов и назначений по подразделению с одной датой
     действия — практичный сценарий и хорошая демонстрация транзакций.
  3. Выгрузка выбранных записей с отбором (сейчас выгрузка — весь справочник):
     добавить фильтры минорной версией контракта, не ломая потребителей.
  Зачем: справочники становятся источником истории, а не только текущих данных.

Б4. УПРАВЛЕНИЕ ТЕСТИРОВАНИЕМ
  1. Карта покрытия: требование → тест-кейс → прогон → дефект, с экраном «что
     не покрыто» (зачатки трассировки у вас есть).
  2. Триаж дефектов: правила автоназначения по модулю и серьёзности плюс поиск
     похожих (возможные дубликаты) — такого нет ни у кого.
  3. Отчёт о прогоне файлом (Excel/PDF) — для сдачи и для отчётности.
  4. Экран метрик качества в реальном времени (pass rate, плотность дефектов,
     доля переоткрытых) — метрики у вас считаются, покажите их.
  Зачем: это то, что отличает «систему тестирования» от «списка кейсов».

Б5. ОТЧЁТНОСТЬ
  1. Довести подписки и расписание доставки: отчёт приходит сам (в описании
     подписки у вас уже есть) — самая заметная для заказчика функция.
  2. Экран актуальности: как давно обновлялись данные по каждому источнику —
     точка «свежесть» уже есть, нужен экран.
  3. Отчёт план-факт с процентом отклонения и прогнозом: план из планирования,
     факт из учёта работ, прогноз из планирования — все данные есть.
  4. Подсказки-определения к показателям на дашборде (что значит каждая мера).
  Зачем: отчётность превращается из «набора кубов» в рабочий инструмент
  руководителя.

Б6. ИНФРАСТРУКТУРА
  1. Панель мониторинга: метрики в коллектор уже идут, но смотреть их негде —
     развернуть панель с готовыми графиками (задержки, ошибки, очереди, базы).
  2. Регулярный бэкап с проверкой восстановления: скрипт есть — сделать
     расписанием и раз в неделю проверять, что восстановление работает.
  3. Сводный каталог событий и мок-сервер по контрактам команд — по решению
     выше это её артефакты.
  4. Сценарий приёмки: одна команда поднимает систему, проходит сквозной
     сценарий, печатает отчёт (проверки примеров у вас уже есть — расширить на
     модули).
  Зачем: среда становится управляемой и проверяемой, а не «набором контейнеров».

================================================================================
В. ЧТО ЭТО ДАЁТ НА ЗАЩИТЕ
================================================================================
1. Демонстрация сквозного сценария на общих данных вместо шести отдельных
   стендов (А1).
2. Подтверждённые числа производительности у каждой команды, а не только у
   отчётности (А6).
3. Состояние системы на одной странице и разбор любой операции по трассировке
   (А2, А3).
4. История проверок интеграций за весь период работы (А5).
5. Отчёты, которые приходят сами, и метрики качества в реальном времени —
   видно, что продукт, а не учебный макет (Б4, Б5).
